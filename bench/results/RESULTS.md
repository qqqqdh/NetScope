# NetScope 실험 결과 (5단계 1차)

측정 환경: 개발 PC(Windows 11, Python 3.13, CPython). 모든 결과는 **시뮬레이터 또는 합성 부하** 기준이며,
실제 네트워크·공개 데이터셋 결과가 아니다. 원자료는 같은 폴더의 `*.txt`, `*.csv`.

## E1 단계별 처리량

| 단계 | 처리량 | 비고 |
|------|--------|------|
| 파싱: Scapy `PcapReader` | 약 1,100 pps | 패킷당 약 1ms. 설계상 예상한 병목 |
| 파싱: 직접 구현한 struct 파서 | 약 82,000 pps | 약 72배. Scapy 결과와 같음을 테스트로 고정 |
| 분석(Flow·집계·탐지), 시뮬레이터 트래픽 | 약 29,000~49,000 pps | 실행마다 편차가 큼(단발 측정 vs 워밍업 후). 두드러진 병목 없음(패킷당 약 20µs) |
| 분석, E4 최악 부하 | 약 19,000~27,000 pps | 모든 상한이 포화되고 축출이 계속 일어나는 상태 |

→ 분석 단계가 새 병목이다. 서버 모드 실효 처리량은 이보다 낮을 수 있다(스냅샷 생성·직렬화 포함).

## E4 최악 부하 메모리 (`e4_*.txt`)

부하 10만 pps(이벤트 시간), 기준선(FastAPI·Scapy import 후) RSS 약 102MB.

| 부하 | 설정 | 최대 RSS |
|------|------|---------|
| concentrated (초기) | Flow 15만, 경고 무제한 보관 | 422MB — 상한 초과 |
| spread (모든 상한 포화) | Flow 15만 | 367MB |
| **spread** | **Flow 10만 (현재 기본값)** | **306MB** |
| **concentrated, 240초** | **Flow 10만 (현재 기본값)** | **361MB** (80초 이후 평탄 → 누수 없음) |

- 발견한 누수: 탐지기가 모든 경고를 영원히 보관하고 있었다(90초에 11,400건). 서버에서는 보관하지 않도록 수정.
- Flow 중복 필드 제거로 약 26MB 절감.
- 목표 320MB는 spread만 충족한다. concentrated는 상한(400MB) 안이지만 목표를 넘는다.
- 살아 있는 데이터(`tracemalloc` 약 162MB + 재정렬 버퍼 약 30MB)보다 RSS 증가가 커서, 나머지는 Python 메모리 파편화로 보인다.

## E5 임계값 민감도 (`e5_pr.csv`)

"hard" 공격: 강도를 기본 임계값에 해당하는 강도의 약 0.1~10배에서 **로그 균등** 분포로 뽑았다(튜닝 시드 100~109, 유형별 30건).
m은 탐지기별 핵심 임계값에 곱한 배수다. Recall은 "약한 공격까지 포함한 전체 공격 중 탐지한 비율"이다.

| m | port_scan R | syn_flood R | dns_flood R | traffic_spike R / P | 정상 시나리오 오탐 |
|---|---|---|---|---|---|
| 0.25 | 0.83 | 0.90 | 0.93 | 0.67 / 0.80 | 급증 7건 |
| 0.5 | 0.57 | 0.77 | 0.77 | 0.67 / 0.80 | 급증 6건 |
| 0.75 | 0.47 | 0.67 | 0.57 | 0.67 / 0.87 | 급증 5건 |
| **1.0 (기본)** | **0.43** | **0.53** | **0.50** | **0.67 / 1.00** | 급증 3건 |
| 1.5 | 0.27 | 0.50 | 0.40 | 0.50 / 1.00 | 급증 3건 |
| 2.0 | 0.23 | 0.47 | 0.37 | 0.47 / 1.00 | 급증 3건 |
| 3.0 | 0.10 | 0.30 | 0.27 | 0.37 / 1.00 | 급증 3건 |

- port_scan·syn_flood·dns_flood는 m=0.25까지 **Precision 1.0, 정상 시나리오 오탐 0건**이다. 시뮬레이터 기준으로는 임계값을 크게 낮출 여지가 있어 보이지만, 시뮬레이터의 정상 시나리오는 실제 네트워크보다 단순하므로 이 결론을 실환경으로 일반화할 수 없다.
- traffic_spike는 m<1에서 오탐이 늘어 정밀도가 떨어지는 트레이드오프가 분명하다. m≥1의 오탐 3건은 대용량 다운로드 시나리오의 low 경고(설계상 허용)다.
- 첫 실행은 강도를 선형 균등 분포로 뽑아 약한 공격이 거의 없었고 Recall이 과대평가됐다(`e5_pr_linear_uniform.csv`, 비교용으로 보관).

## G5 실시간성 (`latency.txt`)

시뮬레이터 1배속, 약 250 pps, 프로세스 내 WebSocket 클라이언트가 스냅샷마다 ack.

| 지표 | P50 | P95 | 목표 |
|------|-----|-----|------|
| Sampled End-to-End | 1.53s | **1.99s** | ≤ 2.5s |
| Snapshot Freshness | 1.00s | **1.02s** | ≤ 1.5s |
| 큐 대기 | 0.1ms | 0.3ms | |
| late_drop 비율 | | **0%** | ≤ 0.1% |

- E2E의 대부분은 초 마감 대기(초 안에서 평균 0.5초) + lateness 1초다.
- 가벼운 부하·브라우저 없는 측정이다. 실제 네트워크·고부하 지연은 live 모드에서 다시 재야 한다.

## E2 큐 크기와 손실 (`e2_queue.csv`, `e2_queue_high.csv`)

실시간 캡처와 같은 조건(소스 스레드가 벽시계 속도로 넣고, 큐가 차면 버림). 각 10~15초.

| 입력 | 큐 1k | 큐 10k | 큐 50k (기본) | 큐 200k |
|------|-------|--------|---------------|---------|
| 5k pps | 손실 0% | 0% | 0% | 0% |
| 20k pps | **7.9%** | 0% | 0% | 0% |
| 40k pps | **22.6%** | **7.3%** | 0% (큐 대기 P95 0.38s) | 0% |
| 60k pps | — | — | **11.5%** (처리 49.7k) | 0%이지만 큐가 계속 쌓임(146k, 대기 P95 2.4s) |
| 80k pps | — | — | **39.8%** (처리 42.9k) | **20.3%** (처리 47.3k, 대기 P95 5.1s) |

- **실시간 지속 처리 상한은 약 50k pps**(이 PC). 그 이상은 큐를 키워도 손실이 지연으로 바뀔 뿐이다.
- **입력이 많을수록 처리량이 오히려 떨어진다**(80k에서 43~47k). 소스 스레드와 분석 워커가 Python GIL을 나눠 쓰기 때문이다. 실제 캡처를 별도 프로세스로 분리하면 개선될 여지가 있다.
- 큐의 역할은 버스트 흡수다. 재정렬 버퍼가 초 마감 때 1초치를 한꺼번에 처리하고 스냅샷을 만드는 동안 워커가 큐를 비우지 못한다(큐 대기 P95가 0.3~0.4초). 필요한 큐 크기 ≈ 입력 pps × 약 0.4초. 그래서 큐 1k는 평균 처리 능력이 충분한 20k pps에서도 손실이 난다.

## E3 lateness 트레이드오프 (`e3_lateness.csv`)

초당 300패킷, 도착 지연 모델: 98%는 0~20ms, 2%는 0~2초. (실제 단일 NIC의 순서 뒤바뀜은 보통 이보다 훨씬 작다.)

| lateness | 늦은 패킷 폐기 | 처리 대기 P50 | P95 |
|----------|----------------|---------------|-----|
| 0.25s | 1.42% | 0.75s | 1.19s |
| 0.5s | 1.18% | 1.08s | 1.48s |
| **1s (기본)** | **0.57%** | 1.39s | **1.99s** |
| 2s | 0% | 2.39s | 2.74s |
| 3s | 0% | 3.35s | 3.70s |

- 처리 대기 ≈ 0.5초 + lateness, P95 ≈ 1초 + lateness.
- **이 지연 모델에서는 G5(종단 간 P95 ≤ 2.5초 그리고 폐기 ≤ 0.1%)를 동시에 만족하는 lateness가 없다.** 1초는 폐기 초과, 2초는 지연 초과. 앞의 G5 통과 결과는 도착 지연이 없는 조건이었다.
- 폐기율이 단순 계산(1초에서 1%)보다 낮은 이유: 초 단위로 마감하므로 같은 초 안에서 늦은 패킷은 버려지지 않는다.
- 권고: 단일 NIC 캡처는 기본 1초. 원격 미러·여러 캡처 지점 병합처럼 도착 지연이 큰 환경은 2초로 올리고 지연 목표를 3초로 완화한다.

## E6 키 테이블 우회 공격 (`e6_eviction.csv`)

느린 스캔(초당 3포트 × 20초) + 처음 보는 출발지의 잡음 SYN. 실행 시간 때문에 키 상한 1,000, 잡음은 상한 대비 비율(동작은 비율이 결정).

| 잡음 (초당 새 키 / 상한) | 0 | 0.5 | 1 | 2 | **3** | 5 | 10 |
|---|---|---|---|---|---|---|---|
| Space-Saving 탐지 | 3/3 | 3/3 | 3/3 | 3/3 | **0/3** | 0/3 | 0/3 |
| LRU 탐지 | 3/3 | 3/3 | 3/3 | 3/3 | **0/3** | 0/3 | 0/3 |

- **설계 문서의 "Space-Saving이 우회 공격에 강하다"는 주장은 틀렸다.** 두 정책이 똑같이 잡음 비율 3에서 함께 무너진다.
- 둘 다 "공격자 속도 vs 잡음 비율" 비교로 귀결된다. LRU는 공격자가 다시 나타나는 간격(0.33초) 안에 상한보다 많은 새 키가 들어오면 밀려나고, Space-Saving은 새 키가 최솟값을 물려받아 테이블 최솟값이 초당 (잡음 비율)만큼 오르므로 공격자의 증가 속도(초당 3)를 넘으면 밀려난다.
- Space-Saving을 유지하는 실제 이유는 판정 보장 하한(부풀린 값으로 경고하지 않음)이다. 이 우회는 `detector_eviction` 품질 경고로 드러난다. 근본 대책(축출 급증 경고, 시간 감쇠 카운터 등)은 v2 과제.

## 실제 캡처 (live) — Windows 11, Npcap 1.90, Wi-Fi (Intel AX201)

`bench/live_check.py`: 캡처 시작·종료 순간에 Windows 어댑터 카운터(송수신 패킷 합)를 읽어 캡처 수와 비교한다.
패킷 내용은 저장하지 않는다. 부하는 Cloudflare 속도 측정 파일 4개 동시 다운로드.

| 경로 | 조건 | NIC 패킷 | 캡처 | 캡처율 |
|------|------|---------|------|--------|
| (측정 방법 검증) | 부하 없음 | 3,633 | 3,634 | 100.0% |
| Scapy 분해 (`AsyncSniffer`) | 다운로드 부하, 1차 | 25,629 | 23,518 | **91.8%** |
| Scapy 분해 | 다운로드 부하, 2차 | 17,155 | 14,048 | **81.9%** |
| **빠른 파서 (`recv_raw` + fastparse)** | 다운로드 부하 | 17,907 | 17,942 | **100.2%** |

- Scapy 경로는 초당 약 1,100개에서 막혀 드라이버 단계에서 8~18%를 잃었다. 이 손실은 NetScope의 `queue_drop`에 잡히지 않는다.
- 빠른 파서로 바꾼 뒤 손실이 사라졌다(100%를 약간 넘는 것은 카운터를 읽는 시점 차이). Wi-Fi 대역폭으로는 더 큰 부하를 만들 수 없어 빠른 경로의 상한은 재지 못했다.
- `live_capture.txt`의 첫 줄(빠른 파서, 151 pps)은 다운로드 부하가 제대로 걸리지 않은 실행이라 비교에서 뺐다.
- 실제 웹 트래픽 20초(약 2만 패킷)에서 경고 0건, 캡처 방향 판정 '양방향', 처리 대기 P95 1.9~2.1초.
- 전체 서버(`--mode live`)로도 실행해 API가 실제 트래픽 스냅샷을 내보내는 것을 확인했다(약 1,360 pps, 손실 0, RSS 114MB).
