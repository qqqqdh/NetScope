# NetScope 설계 제안서

> 실시간 네트워크 트래픽 분석기 — 패킷을 수집해 프로토콜별 통신량, IP 연결 관계, 이상 트래픽을 실시간으로 시각화한다.

- 작성일: 2026-10-21
- 상태: 제안 (검토 대기)

---

## 1. 목표와 범위

### 1.1 목표
| # | 목표 | 성공 기준 |
|---|------|-----------|
| G1 | 패킷 실시간 수집 | 로컬 NIC에서 패킷을 캡처하고, 화면에 1초 이내 지연으로 반영 |
| G2 | 프로토콜별 통신량 | 최근 60초 동안 프로토콜(HTTPS, DNS, SSH 등)별 초당 바이트 시계열과 누적 비율 |
| G3 | IP 연결 관계 | 호스트를 노드, 통신을 엣지로 하는 그래프 (통신량에 비례해 굵기·크기 표시) |
| G4 | 이상 트래픽 탐지 | 포트 스캔, SYN 플러드, DNS 플러드, 트래픽 급증을 탐지해 알림 |
| G5 | 장비 없이 시연·테스트 | 캡처 드라이버나 관리자 권한 없이도 시뮬레이터로 전체 기능 동작 |

### 1.2 범위 밖 (1차 버전)
- 패킷 페이로드 저장, DPI(Deep Packet Inspection), TLS 복호화
- 여러 센서의 분산 수집, 장기 저장소(DB)
- 사용자 인증과 다중 사용자 지원
- 머신러닝 기반 탐지 (규칙 기반 + 통계 기반으로 시작)

## 2. 전체 아키텍처

```
┌──────────────┐   Packet    ┌──────────────────┐  snapshot(1s)  ┌──────────────┐  WebSocket  ┌──────────────┐
│ PacketSource │ ──────────▶ │ TrafficAnalyzer  │ ─────────────▶ │  Web Server  │ ──────────▶ │  Dashboard   │
│  - Live      │  (정규화)    │ AnomalyDetector  │   alerts       │  (FastAPI)   │  REST       │  (브라우저)   │
│  - Simulated │             └──────────────────┘                └──────────────┘             └──────────────┘
└──────────────┘
   캡처 스레드                   스레드 안전(Lock)                   asyncio 루프
```

**핵심 원칙**
1. **캡처 소스 추상화**: 실제 캡처와 시뮬레이터가 같은 `Packet` 모델을 내보내므로, 분석과 표시 계층은 데이터 출처를 구분하지 않는다.
2. **푸시 방식**: 서버는 1초마다 집계 스냅샷을 만들어 모든 WebSocket 클라이언트에 보낸다. 패킷 단위로 보내지 않으므로 트래픽이 많아도 브라우저 부하가 일정하다.
3. **메모리 상한**: 모든 상태는 슬라이딩 윈도우(기본 60초)로 관리하고, 오래된 버킷은 즉시 버린다.

## 3. 기술 스택

| 계층 | 선택 | 이유 |
|------|------|------|
| 언어 | Python 3.12+ (현재 환경 3.14) | 패킷 라이브러리 생태계, 빠른 개발 |
| 패킷 캡처 | **Scapy** + **Npcap**(Windows) / libpcap | 크로스 플랫폼, BPF 필터 지원 |
| 웹 서버 | **FastAPI** + Uvicorn | WebSocket 기본 지원, 비동기 |
| 프런트엔드 | 정적 HTML/JS (빌드 단계 없음) | 의존성 최소화 |

| 연결 그래프 | **D3.js** force layout | 노드·엣지 동적 갱신 |
| 테스트 | pytest, FastAPI TestClient | |

> ⚠️ Windows에서 실제 캡처를 하려면 Npcap 설치와 관리자 권한이 필요하다. 현재 PC에는 Npcap이 없으므로, 기본 실행 모드는 시뮬레이터로 한다.

## 4. 모듈 설계

```
netscope/
├── models.py       # Packet, Alert 데이터 모델
├── protocols.py    # 포트 기반 응용 프로토콜 분류, 내부/외부 IP 판별
├── analyzer.py     # TrafficAnalyzer: 통신량·연결 그래프 집계
├── anomaly.py      # AnomalyDetector: 4종 탐지기
├── sources.py      # LiveSource(Scapy), SimulatedSource
├── server.py       # FastAPI 앱, REST, WebSocket 브로드캐스트
├── __main__.py     # CLI 진입점
└── static/         # index.html, app.js, style.css
tests/
├── test_core.py    # 분류·집계·탐지·시뮬레이터 스펙
└── test_server.py  # API·WebSocket 스펙
```

### 4.1 데이터 모델 (`models.py`)
```python
Packet(ts, src, dst, proto, length, sport=None, dport=None, flags="")
#   proto: TCP | UDP | ICMP | ARP | OTHER
#   flags: TCP 플래그 (Scapy 표기 "S", "SA", "A", "FA", "R" ...)

Alert(ts, type, severity, key, message, details, id)
#   type: port_scan | syn_flood | dns_flood | traffic_spike
#   severity: low | medium | high,  key: 대상 IP 또는 "global"
```

### 4.2 프로토콜 분류 (`protocols.py`)
- 잘 알려진 포트 테이블로 응용 프로토콜을 추정한다. 예: TCP 443 → HTTPS, UDP 53 → DNS, UDP 443 → QUIC, TCP 22 → SSH.
- 요청과 응답 방향을 모두 같은 프로토콜로 분류하기 위해 `sport`와 `dport` 중 **작은 포트부터** 매칭한다.
- 매칭되는 포트가 없으면 L4 이름(TCP, UDP, ICMP, ARP)을 그대로 쓴다.
- 사설·루프백·링크로컬 대역을 "내부(internal)" IP로 판별한다. 그래프에서 색을 구분하는 데 쓴다.

### 4.3 통신량 분석기 (`analyzer.py`)
- **1초 단위 버킷**을 `dict[int초, Bucket]`로 보관한다. 버킷에는 프로토콜별 `[packets, bytes]`와 엣지별 통계가 들어간다.
- 연결 엣지는 방향과 관계없이 `(min(ip), max(ip))`를 키로 묶는다.
- `snapshot(now)`은 `[now-60, now)` 구간을 합산한다. 진행 중인 초는 값이 부분적이므로 제외한다.
- 그래프는 통신량 상위 200개 엣지만 남긴다. SYN 플러드처럼 가짜 출발지가 수천 개일 때 화면이 폭주하는 것을 막기 위해서다.

**스냅샷 스키마**
```json
{
  "ts": 1729500000.0,
  "window": 60,
  "totals":   {"packets": 9120, "bytes": 6400000},
  "lifetime": {"packets": 120000, "bytes": 88000000},
  "rate":     {"bps": 850000, "bytes_per_sec": 106250},
  "protocols": {"HTTPS": {"packets": 5000, "bytes": 4100000}, "DNS": {...}},
  "timeseries": {"labels": [초, ...60개], "series": {"HTTPS": [bytes, ...], ...}},
  "graph": {
    "nodes": [{"id": "192.168.0.2", "bytes": 0, "packets": 0, "peers": 3, "internal": true}],
    "edges": [{"source": "a", "target": "b", "bytes": 0, "packets": 0, "protocols": {"HTTPS": 900}}]
  },
  "top_talkers": [/* 상위 10개 노드 */],
  "alerts": [/* 서버가 덧붙임: 최근 알림 목록 */]
}
```

### 4.4 이상 탐지 (`anomaly.py`)
`observe(packet)`로 패킷을 관찰하고, 서버가 1초마다 `evaluate(now)`를 호출해 새 알림을 받는다.

| 탐지기 | 규칙 | 기본 임계값 | 심각도 |
|--------|------|-------------|--------|
| **포트 스캔** | 한 출발지가 윈도우 안에 SYN을 보낸 **서로 다른 목적지 포트** 수 | 10초 동안 20개 이상 | high |
| **SYN 플러드** | 한 목적지로 온 SYN 수가 많고, ACK보다 훨씬 많으며, **소수 포트에 집중**됨 | 5초 동안 SYN 100개 이상, SYN > 3×ACK, 포트 5개 이하 | high |
| **DNS 플러드** | 한 출발지의 DNS 질의(UDP/53) 수. 터널링이나 감염 의심 | 10초 동안 80건 이상 | medium |
| **트래픽 급증** | 초당 총 바이트를 EWMA 기준선(α=0.1)과 비교 | 10초 학습 후, 평균+4σ 초과 **그리고** 평균의 3배 초과 **그리고** 50KB 이상 | medium |

**설계 결정**
- **포트 스캔과 SYN 플러드 구분**: 스캔도 한 목적지에 SYN을 대량으로 보내므로, 포트 분산도로 둘을 구분한다. 스캔은 여러 포트, 플러드는 한 서비스 포트에 몰린다. 이렇게 하면 같은 사건이 두 가지 알림으로 이중 보고되지 않는다.
- **UDP는 포트 스캔 집계에서 제외**: DNS 응답처럼 임의의 에피메럴 포트로 들어오는 UDP 패킷이 오탐을 일으키기 때문이다.
- **급증 구간은 기준선에 반영하지 않음**: 공격 트래픽이 기준선을 끌어올려 이후 탐지가 둔해지는 것(baseline poisoning)을 막는다.
- **알림 쿨다운 30초**: 같은 `(type, key)` 알림을 반복해서 보내지 않는다.
- 모든 임계값은 `Thresholds` 데이터클래스 하나에 모아 두어, 나중에 설정 파일이나 UI에서 조정할 수 있게 한다.

### 4.5 캡처 소스 (`sources.py`)
- **LiveSource**: Scapy `AsyncSniffer(iface, filter=BPF, store=False, prn=callback)`. 캡처 스레드에서 패킷을 `Packet`으로 변환해 분석기에 넘긴다. IPv4, IPv6, ARP를 지원한다.
- **SimulatedSource**: 시드를 고정할 수 있는 결정적 합성 트래픽 생성기. `generate(t0, duration)`은 순수 함수에 가깝게 만들어 테스트에서 시간을 직접 제어할 수 있게 한다.
  - **정상 트래픽**: 초당 약 150 패킷. 내부 호스트 12대와 외부 서버 약 20곳 사이에서 HTTPS 60%, QUIC, HTTP, DNS, SSH, MySQL, ICMP, mDNS 등을 섞는다. 사인파로 ±20% 변동을 준다.
  - **공격 시나리오** (`attack_interval`마다 순서대로 주입):
    1. 포트 스캔: 외부 IP → 192.168.0.10, 초당 약 60개 포트, 5초
    2. SYN 플러드: 가짜 출발지 수천 곳 → 192.168.0.20:80, 초당 400 SYN, 5초
    3. DNS 플러드: 감염 호스트 192.168.0.66 → 리졸버, 초당 40건, 4초
    4. 트래픽 급증: 대용량 HTTPS 다운로드, 약 900KB/s, 3초

### 4.6 웹 서버 (`server.py`)
| 엔드포인트 | 설명 |
|------------|------|
| `GET /` | 대시보드 정적 페이지 |
| `GET /api/status` | 동작 모드(sim/live), 인터페이스, 수집 PPS, 가동 시간 |
| `GET /api/snapshot` | 현재 스냅샷 (최근 알림 포함) |
| `GET /api/alerts?limit=N` | 알림 이력 (메모리 링버퍼에 최대 500건) |
| `WS /ws` | 접속 즉시 1회, 이후 1초마다 `{"type":"snapshot","data":...}`. 새 알림이 생기면 `{"type":"alert","data":...}`를 즉시 전송 |

- `create_app(mode, iface, bpf, seed)` 팩토리 함수로 앱을 만든다. lifespan에서 소스와 브로드캐스트 루프를 시작하고 종료한다.
- 캡처 스레드와 asyncio 루프 사이의 경합은 분석기 내부의 `threading.Lock`으로 막는다. 스냅샷 생성은 짧은 임계 구역에서 끝난다.

### 4.7 대시보드 (프런트엔드)
```
┌──────────────────────────────────────────────────────────────────┐
│ NetScope   ● LIVE/SIM   850 kbps   152 pps   알림 3   [일시정지]   │
├───────────────────────────────────────────┬──────────────────────┤
│ 프로토콜별 통신량 (누적 영역, 60초)           │ 프로토콜 비율 (도넛)    │
├───────────────────────────────────────────┼──────────────────────┤
│                                           │ 🚨 이상 트래픽 알림     │
│   IP 연결 그래프 (D3 force)                │  - 심각도 색상         │
│   - 노드 크기 = 통신량, 색 = 내부/외부        │  - 클릭 시 그래프에서    │
│   - 엣지 굵기 = 바이트, 색 = 주 프로토콜      │    해당 IP 강조        │
│   - 알림 대상 노드는 빨간 펄스               ├──────────────────────┤
│   - 호버 시 툴팁, 드래그와 줌               │ Top Talkers 표        │
└───────────────────────────────────────────┴──────────────────────┘
```
- 그래프는 노드 id 기준으로 **증분 갱신**한다(기존 노드의 위치 유지). 1초마다 레이아웃이 다시 섞이지 않게 하기 위해서다.
- 다크 테마. 새 알림이 오면 토스트를 띄운다.

| 영역 | 입력 | 기대 결과 |
|------|------|-----------|
| 분류 | TCP→443 / UDP→53 / UDP 53→51000 / TCP 54321→55555 | HTTPS / DNS / DNS / TCP |

| 포트 스캔 | 3초 동안 30개 포트 SYN | 알림 1건(high), 다음 평가에서는 쿨다운으로 중복 없음 |
| 비스캔 | 포트 5개 | 알림 없음 |
| SYN 플러드 | 가짜 출발지 300 SYN, ACK 0 | syn_flood |
| 정상 핸드셰이크 | SYN 300 + ACK 300 | 알림 없음 |
| DNS 플러드 | 4.8초 동안 질의 120건 | dns_flood, key=출발지 |
| 급증 | 30초 동안 약 10KB/s 후 1초 동안 500KB | traffic_spike 1건, 기준선 구간은 0건 |
| 시뮬레이터 | 정상 트래픽만 120초 | **오탐 0건**, 1000 패킷 이상, HTTPS와 DNS 존재 |
| 시뮬레이터 | 공격 주입 120초 | 4종 알림 모두 발생 |
| 서버 | TestClient | status, snapshot 키, WS 첫 메시지, `/` 200 |

## 7. 성능과 한계
- **처리량 목표**: Python과 Scapy 조합으로 초당 수천 패킷 수준. Scapy 파싱이 병목이므로, 고속 링크에서는 BPF 필터로 줄이거나 2단계에서 `pyshark`/`dpkt` 기반으로 교체를 검토한다.
- **메모리**: 버킷 60개 × (프로토콜 수 + 엣지 수)로 상한이 있다. 탐지기 큐도 윈도우가 지나면 비운다.
- **포트 기반 분류의 한계**: 비표준 포트를 쓰는 서비스는 L4로만 분류된다. 2단계에서 SNI나 DNS 응답 기반 도메인 매핑을 추가한다.
- **권한**: 실제 캡처에는 관리자 권한이 필요하다. 대시보드는 기본적으로 `127.0.0.1`에만 바인딩한다(인증이 없기 때문).

| **1단계 (MVP)** | 이 문서의 4~6장: 시뮬레이터와 실제 캡처, 4종 탐지, 대시보드, 테스트 |
| 2단계 | pcap 파일 재생·저장, DNS/SNI 기반 도메인 표시, 임계값 UI 조정, 알림 CSV 내보내기 |
| 3단계 | 지오IP 지도, SQLite 장기 저장과 이력 조회, 통계 기반 이상 탐지 고도화(시간대별 기준선) |

---

## 9. 결정이 필요한 사항
1. **실제 캡처 지원 우선순위**: Npcap을 설치해 1단계에 실제 캡처를 포함할지, 아니면 시뮬레이터만으로 먼저 완성할지
2. **대상 환경**: 개인 PC 모니터링용인지, 서버나 게이트웨이에 두고 원격으로 볼 용도인지 (원격이면 인증이 필요해짐)
3. **프런트엔드**: 정적 JS로 갈지(제안), 아니면 React 등 빌드 기반 프레임워크를 원하는지
4. **탐지 항목 추가 여부**: ARP 스푸핑, 비정상 포트 아웃바운드, 대용량 외부 유출 등
